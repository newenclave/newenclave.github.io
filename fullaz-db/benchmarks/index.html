Same table workload

Every cell stores 24-byte keys and 150-byte values. The key stream is deterministic and unique. The final table contains 1,101,000 records.

Durability is explicit

redb sets Durability::Immediate for every measured write transaction. Fullaz durable paths also synchronize commit data, but recovery semantics differ by backend.

Reads are isolated

Build, point read, range read, and verify run in separate processes. The matrix uses 64 MiB and 1 GiB application-cache settings.

Correctness is checked

Every cell reopens in a final process. The runner checks count, sorted-data digest, and point samples. The orchestrator compares read checksums across cells.

“Cold” calls POSIX_FADV_DONTNEED as a best-effort request. It is not a hardware-cold or cache-free guarantee.

Storage choices

Five page lifecycles, two B+ tree policies

Use the rail to compare the choices. It scrolls horizontally on small screens because these differences are easier to scan as cards than as a narrow table.

Static

A compiled schema stores roots and free-list metadata in a page-zero superblock. It uses physical page IDs and updates pages in place.

No WAL. Controlled images and experiments.

Static WAL

The same physical-page static schema writes redo records before home-page changes. Recovery replays committed records after an interruption.

Normal durable Fullaz starting point.

Virtual static CoW

Components keep stable virtual page IDs. Mutations copy backing pages and update a copy-on-write virtual-page map, then select an alternating superblock.

Crash-consistent experimental storage path.

Dynamic

A persistent component catalog, name indexes, and component metadata sit around the compiled benchmark schema. Pages update in place.

Measures catalog metadata cost, not dynamic key types.

Dynamic WAL

The dynamic catalog path uses the same redo recovery approach as Static WAL.

Durable catalog-oriented configuration.

Neighbor share

When an insertion does not fit, move entries into a sibling first. Split only when sharing cannot make enough room. This produced denser files and generally stronger reads in this workload.

Force split

Skip insertion-time sharing and split the overflowing node. It improved Fullaz bulk and batch writes here, while using roughly 15–19% more allocated space and usually lowering read throughput.

How to read this

A database path comparison, not a B+ tree shootout

What redb represents

redb 4.2.0 is a mature embedded ACID key-value database for Rust. It stores tables in copy-on-write B+ trees, but also has its own MVCC, cache, allocator, transaction protocol, and file layout.

What this isolates

The workload compares one identical ordered byte-table path. It exposes the combined effect of each implementation's B+ tree, schema layer, transaction work, cache, allocator, and durable storage path.

What is not measured

  • Concurrency, snapshots, MVCC behavior, or deletes.
  • Crash injection or recovery time.
  • Tail latency, write amplification, or syscall counts.
  • Different value sizes, skew, or data larger than memory.

One-key writes

redb reaches 726 individual durable transactions per second; Fullaz's best configuration reaches 129. The benchmark does not explain why. A separate I/O trace and syscall benchmark is needed before assigning a cause.
