fullaz-db

Build an embedded database from the page-backed data structures your application needs. Define the schema in Zig. Change different structures in one transaction. Start in memory, then move to files and a WAL.

Open dispatch → See the 60-second example ↓
Not SQL. Not a server.

fullaz-db does not parse SQL or ship a query planner. It composes typed page-backed components at compile time. Raw DynamicDatabase can change a catalog at runtime, but it is a low-level tool, not SQL.

The problem

One storage shape is often not enough

Most embedded databases begin with SQL tables or one sorted key-value interface. Both are good tools. A product with maps, priority work, audit bytes, and an editable document still has to model those shapes above the database.

Spatial data

Map lookup needs boxes and overlap queries. Turning it into string keys or one general table moves index rules into application code.

Priority work

A job scheduler wants a priority queue. A log wants append-only bytes. An editor wants offsets and chunks.

One commit

The application still needs an atomic change across all of these structures, even when each structure has different page rules.

Why fullaz

Compose the database from structures

A Schema is a Zig type. Each selected component owns its root and page kinds. The database type builds bindings, runtime state, and transaction state for those schema fields.

Selected by schema

Only components selected by a schema are instantiated into that database type. There is no runtime registry that constructs every component. Zig can also remove unreachable code, but binary-size claims wait for reproducible benchmarks.

One transaction

A transaction can update a B+ tree, a spatial index, a heap, and a byte store together. The backend owns the commit and rollback boundary.

Same component API

Use the same typed component calls with MemoryDatabase, a static WAL image, or a virtual-page backend. The factory changes storage rules, not the schema shape.

Format is explicit

Page IDs, comparators, component metadata, page kinds, and durable fingerprints are part of the typed configuration. They are not hidden behind an ORM.

60-second example

Declare a schema, commit one change

This database combines an ordered users map, a spatial service-area index, and an append-only audit stream. All names and component options are known when the program is compiled.

const std = @import("std");
const fullaz_db = @import("fullaz-db");

fn compare(_: void, left: []const u8, right: []const u8) std.math.Order {
    return std.mem.order(u8, left, right);
}

const Schema = fullaz_db.Schema(.{ .page_id = u32 })
    .add("users", fullaz_db.bpt(.{
        .compare = compare,
        .CompareContext = void,
        .comparator_id = 1,
        .maximum_key_size = 32,
        .maximum_value_size = 128,
    }))
    .add("service_areas", fullaz_db.rtree(.{
        .Coord = f32,
        .dimensions = 2,
        .maximum_entries = 8,
        .maximum_value_size = 32,
    }))
    .add("audit", fullaz_db.chainStore(.{}));
const Database = fullaz_db.MemoryDatabase(Schema);
const AreaBox = Schema.trait("service_areas")
    .Binding(Database.BackendType).Proxy.BoundingBox;

pub fn main() !void {
    var database = try Database.init(std.heap.page_allocator, .{
        .page_size = 4096,
        .cache_frames = 32,
    });
    defer database.deinit();

    var tx = try database.begin();
    defer tx.deinit();
    if (!try tx.get("users").insert("ada", "Ada Lovelace")) {
        return error.UserAlreadyExists;
    }
    try tx.get("service_areas").insert(
        AreaBox.initWith(.{ 60.16, 24.93 }, .{ 60.18, 24.96 }),
        "helsinki",
    );
    try tx.get("audit").append("created ada\n");
    try tx.commit();
}

The R-tree indexes 2D bounding boxes. Replace MemoryDatabase with StaticDatabaseWithWal when this schema needs a persistent image. The component declarations and transaction calls stay the same.

Backends

Keep the schema, change how pages live

The selected factory defines lifetime, IDs, and recovery behavior. It does not turn fullaz-db into SQL or hide the storage format.

FactoryUse it whenWhat changes
MemoryDatabaseLearning, tests, and short-lived dataNo image exists after deinit().
StaticDatabaseWithWalOne compiled schema owns one persistent imageComponents use physical page IDs. Keep the image and WAL together.
VirtualStaticDatabaseWithWalLogical page IDs matter to the storage designComponents use VIDs. The engine resolves each VID to a physical PID.
VirtualStaticDatabaseWithCowStable logical IDs and copy-on-write commits matterComponents use VIDs. Mutations copy backing pages and virtual-map paths, then select an alternating checksummed superblock.
DynamicSchemaDatabaseWithWalTyped components need durable catalog identity and metadataThe catalog persists, but component names still come from the compiled schema.

Normal persistent path

Start with StaticDatabaseWithWal. A write-ahead log records redo data before image changes, so open() can recover committed work after an interruption.

Experimental storage paths

No-WAL factories update pages in place and are for controlled images. VirtualStaticDatabaseWithCow is an experimental crash-consistent copy-on-write path without WAL, snapshots, or MVCC. Raw DynamicDatabase APIs are for low-level catalog work.

Internals and limits

Explicit storage, not hidden magic

Schema fields (compile time) | +-- component descriptors, fingerprints, page kinds | v typed database bindings and transaction state | v page cache -- optional virtual page map -- device + WAL

What is explicit

  • Page IDs and page kinds.
  • Comparator identity and durable component options.
  • Transaction lifetime and iterator ownership.
  • Physical versus virtual page addressing.

What is not here yet

  • SQL, joins, and a query planner.
  • Snapshots, MVCC, and concurrent access.
  • A stable universal file format promise.
  • Broad workload or production-performance claims.

The API and file formats are evolving. Read the current source and tests before relying on durability or compatibility behavior.
