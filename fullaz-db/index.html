fullaz-db

A typed storage library for Zig. Put page-backed components in a schema. Change them in one transaction. Keep the same component API when you move from memory to files.

Build a first database →
Not SQL

fullaz-db does not parse SQL. The normal typed APIs use a Zig schema. Names such as users are known when your program is compiled. Raw DynamicDatabase can change a component catalog at runtime, but it is a low-level tool and not SQL.

Choose components by data

A component owns one data structure and one root. Components share a transaction. They do not share data.

NeedComponentStores
Sorted recordsbptByte keys and byte values.
Map areasrtreeBounding boxes and byte values.
Next job by priorityslotHeapFixed-size priority keys and values.
One growing blobchainStoreAppendable bytes.
Editable documentweightedSequenceBytes with insert and remove by offset.

Choose one structure before adding it to your schema. Start with the smallest shape that fits your data.

Start with memory

Start with MemoryDatabase. It has no files. Its pages disappear when database.deinit() runs. This makes it useful for learning, tests, and small experiments.

1

Declare one component

This schema has one ChainStore. It stores one appendable byte stream named notes.

const std = @import("std");
const fullaz_db = @import("fullaz-db");

const Schema = fullaz_db.Schema(.{ .page_id = u32 })
    .add("notes", fullaz_db.chainStore(.{}));
const Database = fullaz_db.MemoryDatabase(Schema);

u32 is the page ID type. It is a fixed-width unsigned number, so it is safe to use in a durable format too.

2

Write, commit, then read

A mutable transaction changes data. commit() publishes the change. Reads use getConst() outside the transaction.

pub fn main() !void {
    var database = try Database.init(std.heap.page_allocator, .{
        .page_size = 4096,
        .cache_frames = 32,
    });
    defer database.deinit();

    var transaction = try database.begin();
    defer transaction.deinit();
    try transaction.get("notes").append("first note\n");
    try transaction.commit();

    var output: [64]u8 = undefined;
    const count = try database.getConst("notes").readAt(0, &output);
    std.debug.print("{s}", .{output[0..count]});
}
first note

Add a table and an audit log

A B+ tree is an ordered map. This schema has a users table and an audit byte log. They are separate components.

const fullaz = @import("fullaz");

fn compare(_: void, left: []const u8, right: []const u8)
    fullaz.core.algorithm.Order
{
    return switch (std.mem.order(u8, left, right)) {
        .lt => .lt,
        .eq => .eq,
        .gt => .gt,
    };
}

const Schema = fullaz_db.Schema(.{ .page_id = u32 })
    .add("users", fullaz_db.bpt(.{
        .compare = compare,
        .CompareContext = void,
        .comparator_id = 1,
        .maximum_key_size = 32,
        .maximum_value_size = 128,
    }))
    .add("audit", fullaz_db.chainStore(.{}));

The comparator gives the B+ tree a stable order. comparator_id is the durable ID for that order. Change it if the comparison rules change.

3

Change both components together

One commit publishes the new user and the audit line together. If a try fails first, defer transaction.deinit() rolls back the active transaction.

var transaction = try database.begin();
defer transaction.deinit();

if (!try transaction.get("users").insert("ada", "Ada Lovelace")) {
    return error.UserAlreadyExists;
}
try transaction.get("audit").append("created ada\n");
try transaction.commit();
4

Read a B+ tree value

find() returns an iterator. The iterator can pin a page, so close it before the next write.

var found = (try database.getConst("users").find("ada")).?;
defer found.deinit();

const entry = (try found.get()).?;
std.debug.print("{s}: {s}\n", .{ entry.key, entry.value });

Pick a backend

The typed APIs stay the same. The factory changes how pages live and how the image reopens.

FactoryUse it whenWhat changes
MemoryDatabaseYou are learning, testing, or using short-lived data.There is no image to reopen.
StaticDatabaseWithWalOne compiled schema owns one persistent image.Component pages use physical page IDs. Keep the image and WAL together.
VirtualStaticDatabaseWithWalStable logical page IDs matter to your storage design.Components use VIDs. The engine resolves each VID to a physical PID.
DynamicSchemaDatabaseWithWalTyped components need durable catalog identity and metadata.The catalog is persistent. Component names still come from the compiled schema.

Normal persistent start

Use StaticDatabaseWithWal for a normal durable typed app. A WAL is a write-ahead log. It writes redo data before the image changes, so open() can recover committed work after an interruption.

const Device = fullaz.device.FileBlock(u32);
const Log = fullaz.device.FileLog(u32);
const Database = fullaz_db.StaticDatabaseWithWal(
    Schema,
    Device,
    Log,
);

Virtual addresses

Use virtual static storage only when logical page IDs have value. The component code does not change. The storage format does.

const Device = fullaz.device.FileBlock(u64);
const Log = fullaz.device.FileLog(u64);
const Database = fullaz_db.VirtualStaticDatabaseWithWal(
    Schema,
    Device,
    Log,
);

No-WAL factories are for controlled images and experiments. They do not provide atomic crash recovery. Raw DynamicDatabase APIs are for advanced catalog work, not the normal typed application path.

For exact format() and open() options, read the current source and tests in fullaz.

What DB Lab models

Its visible tables are logical namespaces inside one values B+ tree. They are not runtime-created B+ tree components. Remove can reclaim empty B+ tree pages. It is not a graph garbage collector or a crash simulator.

Planned: virtual dynamic storage

This backend does not exist yet. The goal is a durable component catalog that uses virtual IDs while the device and WAL use physical IDs.

typed components and catalog: VID | v VirtualPageMap: VID -> PID | v physical page cache, device, and WAL: PID

The future typed API still uses a compile-time Schema. It will not add SQL-style runtime CREATE TABLE. Snapshots, MVCC, and old physical page retirement are also future work.
