60-second example

Dynamic schema with a durable catalog

Use a normal compiled Zig schema. Store its component identity and metadata in a durable catalog. Reopen the image through the same typed API.

Dynamic does not mean runtime SQL.

The schema below is still compiled into the program. Dynamic schema storage gives those compiled components durable catalog records. It does not let Python, C++, or application input invent a new transaction.get("name") component.

Why use it

Keep typed calls and persist component identity

A static database stores one closed-world schema in its superblock. A dynamic schema database also keeps a catalog. The catalog records a component ID, page-kind range, descriptor fingerprint, and metadata for every active compiled component.

Use it when

You need typed components with durable catalog identity and metadata. The same application code can still call transaction.get("notes").

Use WAL for files

DynamicSchemaDatabaseWithWal writes redo data before home pages. The log helps open() recover a committed change after an interruption.

Complete example

Format, write, reopen, read

This program formats an image and WAL, appends one note, opens both files again, and prints the note.

const std = @import("std");
const fullaz = @import("fullaz");
const fullaz_db = @import("fullaz-db");

const image_path = "catalog.img";
const wal_path = "catalog.wal";
const page_size = 4096;

const Schema = fullaz_db.Schema(.{ .page_id = u32 })
    .add("notes", fullaz_db.chainStore(.{}));

const Device = fullaz.device.FileBlock(u32);
const Log = fullaz.device.FileLog(u32);
const Database = fullaz_db.DynamicSchemaDatabaseWithWal(Schema, Device, Log);

const options: Database.InitOptions = .{
    .image_id = [_]u8{0xB1} ** 16,
    .cache_frames = 64,
    .components = .{ .notes = .{} },
};

fn formatAndWrite(allocator: std.mem.Allocator, io: std.Io) !void {
    var database = try Database.format(
        allocator,
        try Device.create(io, image_path, page_size),
        try Log.create(io, wal_path),
        options,
    );
    defer database.deinit();

    var transaction = try database.begin();
    defer transaction.deinit();
    try transaction.get("notes").append("catalog-backed note\n");
    try transaction.commit();
}

fn reopenAndRead(allocator: std.mem.Allocator, io: std.Io) !void {
    var database = try Database.open(
        allocator,
        try Device.open(io, image_path, page_size),
        try Log.open(io, wal_path),
        options,
    );
    defer database.deinit();

    var output: [128]u8 = undefined;
    const count = try database.getConst("notes").readAt(0, &output);
    std.debug.print("{s}", .{output[0..count]});
}

pub fn main(init: std.process.Init) !void {
    try formatAndWrite(init.gpa, init.io);
    try reopenAndRead(init.gpa, init.io);
}

The expected output is:

catalog-backed note
What each part does

Four steps, one typed component

1

Declare the schema

Schema names one notes ChainStore. The name and component type are known at compile time.

2

Format the image and log

Database.format creates the database boot state, catalog, component metadata, image, and WAL.

3

Commit one transaction

The transaction appends bytes through the typed ChainStore proxy. Commit writes the normal database changes and catalog-backed metadata through the WAL path.

4

Open and validate

Database.open opens the image and WAL. It checks that the active catalog component agrees with the compiled name, kind, format, and settings before returning notes.

The catalog

Why this is different from a static schema image

The typed application calls look similar for static and dynamic databases. The difference is durable control-plane data.

Component ID

The catalog gives the active notes component a durable identity. The identity is not only its field position in the current process.

Metadata record

Each component stores the state needed to reopen it, such as roots or byte-stream endpoints.

Schema check

Open rejects a catalog entry that does not match the current compiled descriptor, name, version, or fingerprint.

Nested components

Let one B+ tree entry own another B+ tree

hierarchyBpt and hierarchyStore work with typed memory, static, static WAL, virtual static, and dynamic schema databases. The outer tree stores a fixed envelope. That envelope can own the root of an embedded component.

This small example defines one recursive folder type. A folder may contain another folder. With a dynamic schema database, the typed catalog also validates the whole compiled hierarchy when the database opens.

fn compare(_: void, left: []const u8, right: []const u8) std.math.Order {
    return std.mem.order(u8, left, right);
}

const raw_payload_capacity = 32;
const folder_value_size = fullaz_db.value_envelope.envelope_byte_size +
    @max(@sizeOf(u32), raw_payload_capacity);

const Folder = fullaz_db.bpt(.{
    .compare = compare,
    .CompareContext = void,
    .comparator_id = 2,
    .maximum_key_size = 32,
    .maximum_value_size = folder_value_size,
    .fixed_value_size = folder_value_size,
});

const Types = fullaz_db.Hierarchy(.{
    .registry_id = 1,
    .types = &.{.{
        .tag = "folder",
        .type_id = 1,
        .type_version = 1,
        .metadata_format_version = 1,
        .descriptor = Folder,
        .allowed_child_type_ids = &.{1},
    }},
});

const Tree = fullaz_db.hierarchyBpt(Types, fullaz_db.bpt(.{
    .compare = compare,
    .CompareContext = void,
    .comparator_id = 3,
    .maximum_key_size = 32,
    .maximum_value_size = folder_value_size,
    .fixed_value_size = folder_value_size,
}));

const Schema = fullaz_db.Schema(.{ .page_id = u32 })
    .add("tree", Tree);

allowed_child_type_ids = &.{1} means that a folder may embed another folder. An empty list would make the type a leaf.

1

Create the root folder

Insert an embedded folder envelope into the outer typed tree.

var tree = transaction.get("tree");
try tree.insert("root", tree.embed("folder"));
2

Open the folder in place

The editor writes the child root into the parent value. It does not copy the value out and write it back later.

var root = (try tree.openEmbeddedForEdit("root", "folder")).?;
defer root.deinit();

try root.insert("readme", root.raw("folder", "Hello from a folder"));
try root.insert("child", try root.embed("folder"));
3

Finish nested editors from inside out

An open editor holds the parent entry stable. Close the deepest editor first, then commit the database transaction.

var child = (try root.openEmbeddedForEdit("child", "folder")).?;
defer child.deinit();

try child.insert("message", child.raw("folder", "Nested value"));
try child.finish();
try root.finish();
try transaction.commit();
GC follows ownership edges.

Removing root removes its ownership edge. A later Dynamic GC cycle can reclaim the nested folder pages that are no longer reachable. Raw payload bytes stay opaque to GC.

Important boundary

Dynamic catalog, compiled schema

The word dynamic describes the persistent catalog and metadata layer. It does not remove Zig comptime schema composition.

  • Use DynamicSchemaDatabaseWithWal for normal typed application data with a durable catalog and redo recovery.
  • Use raw DynamicDatabase only for low-level catalog tools such as provisioning, rename, drop, or inspection.
  • Do not treat this API as SQL CREATE TABLE or a runtime component factory.
  • Keep catalog.img and catalog.wal together.
